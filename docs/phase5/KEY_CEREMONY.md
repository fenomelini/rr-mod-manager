# Phase 5 Signing Key Ceremony

## Scope

`rrmm-catalog-author` is a separate, non-runtime binary for signing bootstrap,
catalog updates, and online-key revocation. It can:

- Generate root or online Ed25519 key pairs.
- Create generation-1 root metadata delegating one online key.
- Sign root metadata with the offline root key.
- Export a validated, deterministic array of public trust anchors for release builds.
- Create a sequence-1 catalog from reviewed recipe files.
- Sign a catalog with the delegated online key and immediately verify the full
  trust path.
- Authenticate a reviewed predecessor floor and derive the next root generation
  or catalog sequence without accepting manual counters.
- Revoke every previous online key by publishing a higher root generation with
  one new delegation.
- Verify signed metadata without reading or modifying SQLite.

Catalog sequence is monotonic within one root generation. A higher authenticated
root generation starts a new catalog epoch at sequence 1. This permits recovery
if a compromised old online key attempted to poison clients with a very large
sequence. Within an unchanged root generation, `catalog-update` derives exactly
`previous sequence + 1`.

Each higher root generation carries a cumulative `revoked_online_key_ids` list.
`root-update` adds every delegation from the previous root and preserves all
older revocations. A key ID is derived from its public key, so a revoked key
cannot be reintroduced under an alias or after an intervening generation.

No production key has been generated by the repository tests or development
workflow.

## Private-Key Policy

Private key files contain an unencrypted 32-byte Ed25519 seed in a strict JSON
envelope. Use them only on an encrypted, offline volume. The authoring tool:

- Requires an absolute private-key path.
- Requires the `.rrmm-private.json` suffix and rejects paths inside the source
  workspace.
- Requires an existing real parent directory accessible only by its owner.
- Creates private files as `0600` on Unix.
- Refuses symlink traversal, non-canonical parent paths, ownership mismatches,
  non-regular files, and group-readable or world-readable private key files.
- Opens existing keys with `O_NOFOLLOW` and validates the opened descriptor.
- Refuses every existing output path instead of overwriting it.
- Uses same-directory temporary files, file sync, no-clobber persistence, and
  directory sync.
- Derives the key ID from SHA-256 of the Ed25519 public key.
- Never prints private material.
- Zeroizes decoded private-key buffers after use.

Secure private-key creation is currently disabled on non-Unix systems because
owner-only Windows ACL creation has not been implemented. Never place private
keys in this workspace, Git, CI, environment variables, shell arguments,
cloud-synced folders, logs, or release archives.

The offline root key and online signing key should be generated on separate
encrypted volumes. Transfer only public keys and signed metadata between trust
zones.

## Build

Build and test the authoring binary from reviewed source before moving it to an
offline host:

```bash
cargo test --package rrmm-catalog-author --all-targets
cargo build --release --package rrmm-catalog-author
```

Record the source revision and SHA-256 of the release binary in the ceremony
log. The log may contain public keys, key IDs, metadata hashes, timestamps, and
operator approvals, but never a private seed.

## Root Bootstrap

Create an owner-only directory on the encrypted offline root volume:

```bash
install -d -m 0700 /absolute/offline-root/rrmm-root
rrmm-catalog-author key-generate \
  --role root \
  --private-key /absolute/offline-root/rrmm-root/root.rrmm-private.json \
  --public-key /absolute/offline-root/rrmm-root/root.public.json
```

Generate the online key independently on its encrypted signing volume:

```bash
install -d -m 0700 /absolute/online-signer/rrmm-online
rrmm-catalog-author key-generate \
  --role online \
  --private-key /absolute/online-signer/rrmm-online/online.rrmm-private.json \
  --public-key /absolute/online-signer/rrmm-online/online.public.json
```

Transfer `online.public.json` to the offline root host. Choose reviewed Unix
timestamps whose online validity contains the ceremony time and whose end does
not exceed root expiry:

```bash
rrmm-catalog-author root-bootstrap \
  --online-public-key online.public.json \
  --valid-from <unix-seconds> \
  --valid-until <unix-seconds> \
  --expires-at <unix-seconds> \
  --output root-metadata.json

rrmm-catalog-author root-sign \
  --private-key /absolute/offline-root/rrmm-root/root.rrmm-private.json \
  --metadata root-metadata.json \
  --output signed-root.json
```

After independent verification, disconnect the root volume and retain at least
two geographically separate encrypted offline backups. The public root record
is the value that must later be embedded into production RRMM builds.

On the clean release-verification host, export the reviewed public root into a
new file (the authoring tool never overwrites an existing path):

```bash
rrmm-catalog-author trusted-roots-export \
  --trusted-root root.public.json \
  --output production-roots.reviewed.json
```

Compare its key ID and SHA-256 against the ceremony log, obtain two-person
approval, then use its exact JSON array as `trust/production-roots.json` in the
release checkout. `apps/cli/build.rs` rejects empty, malformed, duplicate, or
incorrectly derived anchors and blocks a release build before this handoff is
complete. Root-anchor replacement requires a new application release and a
separate migration review.

## Catalog Bootstrap

On the online signing host, create sequence 1 from reviewed authoring recipes:

```bash
rrmm-catalog-author catalog-bootstrap \
  --recipe recipes/compatibility/23896268/unrewound-tape-fee--employee-fee-policy.json \
  --issued-at <unix-seconds> \
  --expires-at <unix-seconds> \
  --output recipe-catalog.json

rrmm-catalog-author catalog-sign \
  --private-key /absolute/online-signer/rrmm-online/online.rrmm-private.json \
  --trusted-root root.public.json \
  --root-metadata signed-root.json \
  --catalog recipe-catalog.json \
  --output signed-catalog.json
```

`catalog-sign` requires the catalog window to fit completely inside both root
and delegated-key validity. It then verifies the new signatures with the real
system clock before publishing the signed output.

## Independent Verification

On a clean release-verification host:

```bash
rrmm-catalog-author verify \
  --trusted-root root.public.json \
  --root-metadata signed-root.json \
  --recipe-catalog signed-catalog.json > trust-floor.json
```

The command is read-only and prints only the next rollback floor. Confirm:

- Root generation is `1`.
- Catalog sequence is `1`.
- Public key IDs match the ceremony log.
- Payload hashes match independently transferred copies.
- All validity windows and artifact hashes are correct.
- The catalog contains only approved recipes.

Do not publish until two-person review confirms the public root, signed root,
signed catalog, package catalog, RRMM bundles, and release notes.

Preserve `trust-floor.json` as public ceremony evidence. Every update command
requires this exact reviewed predecessor. Signature validity alone is not enough
to select a predecessor because an older authentic file could create a fork.

## Routine Catalog Update

When root metadata and the online key remain current, use the same signed root
as both previous and current root. The command authenticates the previous
catalog against `trust-floor.json` and derives sequence + 1:

```bash
rrmm-catalog-author catalog-update \
  --private-key /absolute/online-signer/rrmm-online/online.rrmm-private.json \
  --trusted-root root.public.json \
  --floor trust-floor.json \
  --previous-root-metadata signed-root.json \
  --previous-catalog signed-catalog.json \
  --root-metadata signed-root.json \
  --recipe recipes/compatibility/23896268/unrewound-tape-fee--employee-fee-policy.json \
  --issued-at <unix-seconds> \
  --expires-at <unix-seconds> \
  --output signed-catalog.next.json
```

Verify the result against the previous floor and replace the ceremony floor only
after independent approval.

## Online-Key Rotation

Generate a new online key on a separate owner-only encrypted volume, then move
only its public record to the offline root host. `root-update` authenticates the
previous root against the reviewed floor, requires a different online key,
removes every old delegation, derives root generation + 1, and signs directly:

```bash
rrmm-catalog-author root-update \
  --private-key /absolute/offline-root/rrmm-root/root.rrmm-private.json \
  --trusted-root root.public.json \
  --floor trust-floor.json \
  --previous-root-metadata signed-root.json \
  --online-public-key online-2.public.json \
  --valid-from <unix-seconds> \
  --valid-until <unix-seconds> \
  --expires-at <unix-seconds> \
  --output signed-root.next.json
```

On the new online signer, authenticate the previous catalog and publish sequence
1 in the new root epoch:

```bash
rrmm-catalog-author catalog-update \
  --private-key /absolute/online-signer-2/rrmm-online/online-2.rrmm-private.json \
  --trusted-root root.public.json \
  --floor trust-floor.json \
  --previous-root-metadata signed-root.json \
  --root-metadata signed-root.next.json \
  --recipe recipes/compatibility/23896268/unrewound-tape-fee--employee-fee-policy.json \
  --issued-at <unix-seconds> \
  --expires-at <unix-seconds> \
  --output signed-catalog.next.json
```

The historical authentication used to derive counters deliberately ignores the
current clock so an expired predecessor can be renewed. It still requires valid
signatures, strict schemas, exact reviewed payload hashes, and validity-window
containment. The newly produced root and catalog must be currently valid and
pass normal runtime verification before publication.

Within the same root generation, `--previous-catalog` is mandatory and must
match the complete reviewed floor. When root generation advances, the new epoch
can start from the reviewed floor without possessing the old catalog bytes. This
keeps emergency recovery possible even if a malicious high-sequence catalog is
known by hash but no longer retrievable.

## Emergency Handling

If the online key is suspected compromised, stop catalog publication and run the
online-key rotation flow with a freshly generated replacement. The higher root
generation contains only the new key, so catalogs signed by the revoked key are
rejected. Revoked IDs remain cumulative in every later root. The new root epoch
starts at catalog sequence 1 and supersedes any sequence accepted under the
compromised generation.

Do not delete or rewrite the reviewed predecessor floor. If the offline root
private key is compromised, metadata rotation is insufficient because that key
is the pinned trust anchor. Recovery requires a new application release with a
new embedded root public key and a separately reviewed migration plan.
